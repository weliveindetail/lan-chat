# Qwen chat for a friend: basic setup

**Date:** 2026-11-07

## Goal

Let a friend chat with the local Qwen model from their laptop when they visit the office. They already have LAN access and mainly want to chat, so they don't need a coding agent, and they shouldn't have to install anything.

## Decision

A web page on this machine, reached over the LAN with HTTPS and no password:

```text
Friend's browser --LAN, HTTPS--> lan-chat server --loopback--> Ollama (qwen3.6:35b)
```

| Part | Choice | Status |
|---|---|---|
| Model | `qwen3.6:35b` in Ollama, staying on `127.0.0.1:11434` | Running |
| Backend | Python standard library server, [lan-chat/server.py](../lan-chat/server.py) | Built and tested |
| Frontend | assistant-ui (React), built with Vite into static files, source in `lan-chat/frontend/` | Built and tested in headless Chromium and Firefox, works with the existing CSP |
| Hosting | systemd service under a no-login `lan-chat` account, code in `/opt/lan-chat`, started on demand | Draft, never run |
| Address | `https://192.168.50.142:8080` with a self-signed certificate | Not set up |

## What the backend enforces

- HTTPS when given a certificate and key
- Chat requests from other websites are rejected
- The model is forced, and only `messages` and `stream` are accepted from the client
- All other Ollama routes are unreachable
- Limits of 1 MiB per request, 200 messages, 8192 output tokens and 2 active chats
- Hidden reasoning never reaches the browser
- No chats are stored on the server, so history stays in the browser

The HTTP API is documented in [lan-chat/README.md](../lan-chat/README.md).

## Accepted limits

- **No password:** only a few people have access to the Wi-Fi, so the password was dropped. Anyone who can reach the port can use the model.
- **Self-signed certificate:** chats are encrypted, but the friend must accept a browser warning. Someone on the LAN could impersonate the server unless the fingerprint is compared.
- **Shared model:** the friend's chats compete with my own Ollama use.

## Alternatives ruled out

- **Sharing the `ez` account:** it is in `sudo` and `docker`, so this effectively gives root.
- **Exposing Ollama on the LAN:** it has no authentication, and its API can delete or pull models.
- **SSH tunnel with Qwen Code on the friend's laptop:** too much setup for chatting.
- **Guest Linux account on this machine:** gives a real shell, which chatting doesn't need.
- **`qwen serve` Web Shell:** its token grants full code execution.
- **Open WebUI:** a much larger app that hasn't been audited, and its README doesn't cover telemetry or whether all outside connections can be turned off. Reconsider it if saved history, accounts or file uploads become necessary.
- **LibreChat and LobeHub:** far more than one person chatting needs.
- **Chainlit:** the repo was archived on 2026-10-15.

## Frontend results

- No Node process is needed at runtime, and the CSP did not have to change.
- The UI was tested through the real `server.py`, using a fake model for the failure cases and a few short prompts against `qwen3.6:35b`. It was retested over HTTPS after the password was removed.
- History is kept in `sessionStorage`, so it survives a reload and ends when the tab closes.
- Images in model replies are never loaded, because the CSP would block them and a fetch could leak data.

## Next steps

1. Run `install.sh` and start the service. The hardening options could break it on first start.
2. Reserve `192.168.50.142` on the router, because it comes from DHCP and the service can't bind if it changes.
3. Run `sudo ufw status verbose` to see whether the firewall allows or blocks the port, and add a rule if needed.
4. Test from the friend's laptop or another LAN device, including accepting the certificate warning, ideally on a phone too.

## Still untested

- Whether Ollama actually stops generating when a client disconnects. The browser and `server.py` do close their connections on Stop, but Ollama's own behaviour wasn't observed.
- Clicking through the real certificate warning, because the automated tests skip it
- Real phones and Safari. Phone widths were only emulated.
- The systemd service, LAN access and the firewall rule

## Open choice

Thinking is on by default, which means a short wait before each answer. `--no-think` is faster, but answers may be weaker. The current preference is to leave it on.
